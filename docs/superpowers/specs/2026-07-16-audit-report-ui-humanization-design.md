# 검증보고서 UI 업무용 문구 정리 설계

## 목적

감사자가 읽는 검증보고서에서 시스템 코드와 프로그래밍 용어를 제거하고,
검증 의미와 근거 위치를 업무용 한국어로만 전달한다. 변경은 표시 계층에
한정하며 검증 엔진의 판정과 산출물 계약은 유지한다.

## 성공 기준

- HTML과 DOM에 검증 ID·유형 코드, 영문 자동 해석 사유 코드, 원시 근거 경로,
  `기술 세부정보`, `issue` 표현이 남지 않는다.
- 사용자 문구에 `파싱`, `배치되지 않은 검증`, `근거 연결 실패` 같은 구현 관점의
  표현이 남지 않는다.
- 검증 범례는 그룹별 상태 건수와 한국어 검증 방법만 표시한다.
- 자동 해석이 어려운 항목은 한국어 사유, 사람이 확인할 항목, 검토 안내만
  표시한다.
- 드릴다운의 검증 방법, 허용오차, 판정 사유, 사람이 읽을 수 있는 근거 위치와
  원문 이동 기능은 유지한다.
- `CheckResult`의 상태, 금액, ID, 순서와 검증 엔진 출력은 변경하지 않는다.
- 공통 HTML 렌더러를 사용하는 verify-app도 동일한 화면 계약을 따른다.

## 범위

### 포함

- `report_html.py`의 범례, 드릴다운, 자동 해석 확인 패널 문구와 마크업
- 상태 배지, 진행상황, 확인 필요 패널에 남은 구현 관점 진단 문구
- 위 영역의 여백, 정보 위계, 카드 및 반응형 가독성
- `report_frame.py`의 기존 한국어 검증 방법 레지스트리 재사용
- 엔진이 생성한 영문·코드형 검증 제목과 판정 사유의 공통 표시 변환
- HTML 공통 렌더러를 통한 verify-app 표시 일치
- 감사용 Excel에서 발견되는 내부 코드 노출 확인과 필요한 최소 표시 수정
- 렌더링 회귀 테스트와 브라우저 시각 QA

### 제외

- 검증 결과 생성, 상태 분류, 금액 계산, 허용오차 계산
- `check_id`, `check_type`, 근거 원시 경로 등 내부 데이터 계약 변경
- 새로운 검증 유형이나 진단 체계 추가
- 별도 개발자 모드 또는 진단 로그 화면 신설
- 보고서 전체 디자인 개편

## 표시 설계

### 검증 범례

범례의 각 항목은 코드와 설명의 2열 구성을 없애고 한국어 검증 방법을 한 줄로
표시한다. 그룹명과 상태별 건수는 유지한다. 등록되지 않은 유형은 내부 값을
노출하지 않고 `기타 검증 방법`이라는 중립 문구를 사용한다.

### 검증 상세

`기술 세부정보` 영역과 원시 근거 경로를 마크업에서 제거한다. 기존 근거 표의
사람이 읽을 수 있는 위치와 원문 이동 동작은 유지한다. 자동 해석 사유는 영문
코드 없이 한국어 설명만 별도 안내 상자에 표시한다. 검증 방법과 허용오차,
판정 사유의 순서는 유지해 기존 감사 흐름을 보존한다.

드릴다운을 여닫는 DOM 식별자는 `check_id`로 만들지 않고 렌더링 순서에 기반한
불투명한 화면 전용 식별자를 사용한다. 검증 결과의 순서와 내부 ID 자체는 바꾸지
않는다.

엔진이 생성한 `FS to note match`, `BS equation`, 영문 판정 사유와 코드형 제목은
표시 계층의 공통 변환 함수에서 업무용 한국어로 바꾼다. 의미를 안전하게 보존할
수 없는 내부형 문구는 검증 유형별 한국어 표시명과 상태별 중립 사유로 대체한다.
원본 제목과 사유 값은 변경하지 않는다.

### 자동 해석 확인

패널 제목은 `자동 해석 확인`, 설명은 `원문 구조를 자동으로 확정하지 못해
사람의 확인이 필요한 항목입니다.`로 바꾼다. 카드에는 검증 제목, 한국어 사유,
사람이 읽을 수 있는 확인 대상만 표시한다. 원시 출처 문자열과 영문 사유 배지는
제거하고 `issue를 제보하세요`는 `원문에 해당 항목이 있다면 검토를 요청하세요.`로
바꾼다.

### 공통 상태 및 진행 문구

사용자 화면의 `파싱 불확실`은 문맥에 따라 `자동 해석 확인` 또는 `해석 확인
필요`로 통일한다. 렌더러 자체 점검인 `배치되지 않은 검증`과 `근거 연결 실패`는
각각 `보고서 표시 확인 필요`, `원문 위치 확인 필요`로 바꾼다. 내부 집계 키와
상태 값은 그대로 둔다.

### 서식

- 범례 목록은 단일 열로 바꾸고 항목 사이 간격과 행간을 늘린다.
- 자동 해석 확인 카드는 사유와 확인 대상을 시각적으로 구분한다.
- 드릴다운의 검증 방법과 판정 사유 사이 여백을 정돈한다.
- 모바일 너비에서도 코드용 고정 열이 남지 않도록 한다.
- 기존 색상 토큰과 컴포넌트 스타일을 재사용하고 새로운 디자인 체계는 만들지
  않는다.

## 데이터 흐름과 불변 조건

`CheckResult`와 `CheckEvidence`는 변경 없이 렌더러로 전달된다. 렌더러는
`CHECK_METHOD_DESCRIPTIONS`, 검증 유형별 한국어 표시명, 한국어 사유 변환 함수로
사용자 문구를 선택하며,
원시 내부 값은 라우팅과 원문 이동 계산에만 사용하고 최종 HTML 문자열에는
삽입하지 않는다. 화면 상호작용용 ID는 렌더링 순서로 새로 만든다. verify-app은
`_build_html(...)` 결과를 그대로 사용하므로 별도
문구 사전을 추가하지 않는다. Excel의 검증 제목·상태·판정 사유도 같은 표시
함수를 사용하며 별도 사전을 두지 않는다.

## 예외 처리

- 알 수 없는 검증 유형: `기타 검증 방법`
- 알 수 없는 자동 해석 사유: `원문 구조를 자동으로 확정하지 못했습니다.`
- 근거 위치를 사람이 읽는 문구로 변환할 수 없음: 원시 경로를 대신 노출하지
  않고 `근거 위치 확인 필요`로 표시
- 근거가 없음: 기존 기타 검증 배치와 검증 건수는 유지

## 테스트 및 QA

1. 실패 테스트를 먼저 추가해 범례에 `check_type` 코드가 없고 한국어 설명만
   있는지 확인한다.
2. 실패 테스트를 먼저 추가해 상세 HTML에 검증 ID, `기술 세부정보`, 원시 근거
   경로, 영문 자동 해석 코드가 없음을 확인한다.
3. 실패 테스트를 먼저 추가해 자동 해석 확인 패널의 한국어 사유와 안내 문구를
   확인한다.
4. 실패 테스트를 먼저 추가해 모든 사용자 화면에서 `파싱`, `배치되지 않은 검증`,
   `근거 연결 실패`가 업무 문구로 바뀌는지 확인한다.
5. 실패 테스트를 먼저 추가해 영문·코드형 제목과 판정 사유가 HTML과 Excel에서
   동일한 한국어 문구로 표시되는지 확인한다.
6. 최소 렌더러 및 CSS 변경으로 각 테스트를 통과시킨다.
7. verify-app HTML 일치 테스트와 Excel 표면 테스트를 실행한다.
8. `uv run pytest`와 린트 검사를 실행한다.
9. 대표 보고서를 데스크톱과 모바일 너비로 렌더링해 범례, 상세, 자동 해석 카드의
   잘림, 과밀, 정보 위계와 내부 문자열 미노출을 시각 확인한다.
